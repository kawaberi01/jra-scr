# 競馬YouTubeの買い目・思考方法分析：スキル化前段資料

作成日：2026-10-02／文書版：0.2（Jevによる分類工程を追加）

対象例：競馬ゆっくり https://www.youtube.com/@hitokuchiyamero

## 1. 目的と現在の確認状況

公開動画を漏れが追える台帳にし、過去の買い目と判断理由を出典時刻付きで保存する。公式結果との照合と、判断基準の変遷を整理する。別の会話・担当でも同じ保存データから再開できる手順を、後でCodexスキルにするための設計資料である。

確認済み：対象チャンネル名・ID（UCWn80UpjQ38NfRjwVe8ir6w）、公開ページの一部動画情報、一覧・字幕取得に使うツールの公式資料。

未確認：公開動画の正確な全件数、対象動画の字幕取得率、抽出精度、作業時間、字幕取得コマンドの対象チャンネルでの実行結果。本資料のコマンドは実施候補であり、実証済み手順ではない。約1,500本という前回の参考値は第三者集計であり、処理対象件数には使わない。

今回の成果物は本資料のみ。全件収集、音声取得、スキル登録、既存analysis.sqliteへの書き込みはまだ実施しない。

## 2. 「動画のスクリプト」を取得する意味

基本想定は動画の字幕・自動字幕から発言記録を取得すること。制作者の元台本とは区別する。

| 資料 | 取得・使用方法 | 限界 |
|---|---|---|
| 手動字幕 | 公開字幕が取得できれば第一候補 | 発言の省略や編集の可能性がある |
| 自動字幕 | 手動字幕がなければ採用 | 馬名、数字、否定表現の誤認を確認する |
| 元台本 | 制作者等から提供された場合に使用 | 公開URLだけで取得できるとは想定しない |
| 音声文字起こし | 字幕なしで音声を用意できた動画の補完 | 文字起こしにも誤認があり、画面情報は含まれない |
| 画面の文字・買い目表 | 該当時刻の画面を確認し記録。必要時にOCRを補助利用 | OCRだけで馬券を確定しない |
| タイトル・概要欄 | 分類や関連動画の発見に使用 | 発言全文・公開当時の内容の代わりにはならない |

原資料と整形済みテキストを分けて保存する。字幕は発言抽出の入口であり、全買い目の確定資料にはならない。字幕も映像も未確認の箇所は「不明」とする。

YouTube Data APIの字幕ダウンロードは動画編集権限が必要なため、第三者チャンネルの全字幕取得には使えない。公開字幕取得はyt-dlpで少数試行し、取得できない場合は未取得として残す。アクセス制限を自動的に回避する手順は設けない。[公式字幕API](https://developers.google.com/youtube/v3/docs/captions/download)

## 3. 入力と処理範囲

開始時に次をconfig.jsonへ固定する。

- チャンネルURLと確認できたチャンネルID。
- 対象範囲：通常動画・Shorts・公開ライブアーカイブ。公開前ライブは待機対象として分ける。
- 棚卸し日時（UTCのISO 8601）、言語（日本語）、期間指定の有無。
- 実行モード：棚卸し／試行／バッチ抽出／目視確認／結果照合／集計／追加更新。
- 保存先の絶対パス、バッチ上限（試行5本、通常20本を初期値とする）。
- 使用したPython・uv・yt-dlp等の実バージョン、実行引数。
- LLMを使う場合のモデル名、抽出プロンプト版、スキーマ版。外部APIを使う場合は呼び出し数・費用上限。
- Jevを使う場合は判定質問・ラベル定義・分類版、入力資料の範囲とハッシュ、モデルID、API応答、使用量も記録する。

「全動画」は棚卸し時点で発見した公開動画を意味する。削除・非公開・未発見の限定公開動画を含む完全な投稿履歴は保証できない。後日取得不能になっても既存台帳から消さず、状態を更新する。

タイトルに「予想」とあっても発走後の動画は事前予想と扱わない。タイトル・概要欄は変更され得るため取得日時も保存する。過去の編集履歴が分からない場合、その限界を付記する。

## 4. 保存構成とデータ契約

初期実装はUTF-8のJSON/JSONLと原資料で完結させる。SQLiteは件数・検索需要に応じて同じデータから生成する。既存競馬DBへ取り込む設計は別作業とする。

```text
<作業ルート>/
  config.json
  inventory.jsonl                 動画台帳、動画IDで一意
  batches/<batch_id>.json         処理順・開始終了時刻・対象ID
  raw/<video_id>/<acquisition_id>/ メタデータ、原字幕等
  normalized/<video_id>/<source_hash>.jsonl
  extracted/<video_id>/<extraction_id>.json
  reviews.jsonl                   確認・訂正の追記履歴
  results.jsonl                   公式結果と出典
  reports/                        買い目一覧、思考方法、未確認一覧
  progress.json                   件数、停止理由、次回の対象
```

動画タイトルをパスに使わず、IDを使う。原字幕・取得済みメタデータを再取得結果で上書きせず、取得回ごとに保存する。

| データ | 必須項目 |
|---|---|
| 動画台帳 | video_id、channel_id、URL、タイトル、公開時刻または不明、取得日時、取得元、各工程の状態、エラー分類、試行回数 |
| 字幕区間 | segment_id、start_sec、end_sec、text、source_type、language、原資料相対パス、SHA-256 |
| 発言抽出 | extraction_id、video_id、segment_id一覧、発言時刻、race_ref、段階、発言種別、構造化内容、根拠、確認状態、プロンプト・スキーマ版 |
| 買い目 | 券種、馬名・馬番、BOX/流し/フォーメーション等の形式、各組または各着順候補、点数、金額・単位・配分、提案/購入申告/回顧の別 |
| 確認履歴 | 対象抽出ID、確認時刻、音声/画面/公式資料、確認結果、訂正前後、確認担当 |
| 公式結果 | race_ref、開催日・場・R、着順、券種別払戻、払戻の単位、出典URL、取得時刻 |

race_refは開催日・競馬場・Rが確定するまでは仮IDとする。年、場、Rをレース名から推測で確定しない。1動画の複数レース、1レースの複数動画を関連付ける。

発言種別は「印」「買い目」「理由」「条件付き判断」「事後説明」「雑談」等。理由タグは能力・展開・馬場・距離/コース・枠・騎手・状態・人気/オッズ等を初期候補とし、新しいタグは辞書版を上げて追加する。

金額不明はnull。『10倍ベット』は相対配分として記録し、1単位の金額が確認できなければ円に変換しない。購入申告は実購入の独立証明とは区別する。

## 5. 実行手順

### 手順0：環境と保存先を確認

uv・RTKの利用可否、空き容量、保存先、既存成果物を確認する。試行にはuvの一時ツール実行を使い、継続実装時に依存バージョンを固定する。既存プロジェクトへ依存を追加する前に、専用作業ルートで完結する構成を優先する。

### 手順1：公開動画を棚卸し

1. 通常動画、Shorts、ライブの一覧をそれぞれ取得する。
2. 各一覧を動画IDで統合する。ページ継続取得が途中で失敗した場合は棚卸しを未完了にする。
3. 件数、重複、最古・最新の動画を確認する。チャンネル表示件数と差がある場合は差と確認状況を記録する。
4. 完了した一覧をスナップショットとして保持し、以降の処理の母集団を固定する。

一覧取得の初期候補はyt-dlpのflat playlist。APIキーが用意できる場合は公式APIでチャンネルのuploads playlistを取得し、playlistItems.listのnextPageTokenがなくなるまで巡回する。表示タブの一覧との照合にも使う。[Channels.list](https://developers.google.com/youtube/v3/docs/channels/list)、[PlaylistItems.list](https://developers.google.com/youtube/v3/docs/playlistItems/list)

試行用コマンド例（標準出力は実装時にUTF-8で保存する。PowerShellの既定リダイレクトに依存しない）：

```powershell
rtk uvx yt-dlp --ignore-config --version
rtk uvx yt-dlp --ignore-config --flat-playlist --skip-download --dump-single-json "https://www.youtube.com/@hitokuchiyamero/videos"
```

同様にURL末尾を /shorts、/streams にして取得する。大量JSONは会話に全文表示せず、保存ファイルと要約を確認する。flat取得だけでは公開日時等が欠けるため、抽出対象動画の詳細メタデータを後から取得する。

### 手順2：5本で字幕取得を実証

台帳をタイトルと概要で仮分類し、異なる年代の予想2本、回顧1本、理論1本、残る種類1本を選ぶ。適合動画がなければ代替理由を記録する。分類は本文取得後に再判定する。選択した動画ID・順序をバッチファイルへ保存する。

1本で利用可能字幕を確認するコマンド例：

```powershell
rtk uvx yt-dlp --ignore-config --skip-download --list-subs "https://www.youtube.com/watch?v=<video_id>"
```

字幕一覧で確認した日本語の言語コードを指定し、1本ずつ取得する。

```powershell
rtk uvx yt-dlp --ignore-config --skip-download --write-info-json --write-subs --write-auto-subs --sub-langs "ja" --sub-format "vtt" -P "<新規の取得回フォルダー>" -o "%(id)s.%(ext)s" "https://www.youtube.com/watch?v=<video_id>"
```

この例のjaは実際の字幕一覧に合わせる。手動・自動が同じ保存名になる場合があるため、両方を保存する実装では取得回または種類別フォルダーを分ける。存在した字幕が取得できない状態と、字幕が存在しない状態を区別する。正常終了コードだけで成功とせず、非空の字幕ファイルと区間数を確認する。

yt-dlpの候補オプションは公式READMEで確認したもの。実行環境のバージョンで試行し、確定後は `rtk uvx --from "yt-dlp==<検証済み版>" yt-dlp ...` のように固定する。必要な追加ランタイムは実エラーと公式資料に基づいて導入し、環境記録へ残す。[yt-dlp公式資料](https://github.com/yt-dlp/yt-dlp)

字幕なしは、文字起こし待ちとして残す。音声を用意できる場合に既存の文字起こしツールを試す。ツール・モデルは日本語馬名の精度、PC性能、処理時間を5本試行後に決め、採用版を固定する。音声が用意できない場合は目視・聴取確認か未確認扱いとする。

### 手順3：時刻付きテキストへ整形

VTTは既存パーサー（候補：webvtt-py）で読む。字幕制御タグを除き、隣接区間の重複表示を整理する。重複除去前の原字幕、元区間ID、元時刻は保持する。離れた時刻の同文は消さない。元区間へ戻れない要約テキストだけを保存しない。

馬名の表記修正は原文とは別フィールドに置き、修正理由を残す。最初・中間・最後の区間を音声と照合し、時刻のずれを確認する。

### 手順4：買い目と判断理由を抽出

整形済み区間を時刻順に分割し、境界に重複区間を設けて文の切断を防ぐ。抽出は原文の範囲内で行う。概要欄を使う場合も別資料として出典を明示する。

LLM抽出指示の核：

> 対象区間で明示されたレース、印、買い目、金額、判断理由、条件、事後説明をJSONとして抽出する。各項目に根拠区間IDと動画時刻を付ける。分からない値はnullとし、本命から単勝購入等を補完しない。冗談と購入申告が曖昧なら曖昧と記録する。与えた公式スキーマ以外のキーを追加しない。

JSONの型・必須項目、出典区間の実在、時刻範囲を機械検証する。分割境界の重複は出典区間と内容で統合し、途中の意見変更は別の発言として残す。抽出時は公式結果を入力せず、事後情報から予想を再構成しない。

1回の抽出で確定とせず、買い目・金額・消し・否定・条件付き判断を音声または画面で確認する。

### 手順5：20〜30本で品質・工数を測る

5本で取得経路が成立した後、固定台帳から年代と分類を分散させて計20〜30本まで増やす。選択IDと選択規則を保存する。発見した字幕なし等の失敗例も残し、都合のよい成功例だけを集計しない。

記録する指標：取得成功/字幕なし/取得失敗の件数、全体と分類別の取得率、確認した買い目の件数、買い目抽出漏れ・誤り、確認時間、文字起こし時間、LLM使用量。買い目抽出漏れは字幕だけとの照合では測れないため、試行内の予想動画は全編を確認する。

全件展開の初期判定基準：

- 買い目・理由に根拠時刻があり、元資料へ戻れる。
- 買い目の誤りと漏れが試行の全編確認で測定され、訂正済み。
- 曖昧な金額や字幕なしを推測で埋めていない。
- 中断・再実行で原資料が失われず、完了項目が重複しない。
- 件数と実測時間から、全件の取得・確認コストを分けて見積もれる。

重大な買い目誤認が残る場合は「全自動で確定」を採用せず、自動抽出後に全買い目を確認する運用へする。試行が合格しても、全件の正確性を保証するものではない。

### 手順6：全件を小分けに処理・再開

固定台帳の公開時刻昇順、同時刻は動画ID順で、未完了の20本をバッチに固定する。公開時刻不明は別キューにする。分類にかかわらず全件に字幕取得等の処理結果を残す。理論・雑談も本文を確認し、思考方法に関係する発言を拾う。

1動画の処理終了ごとに状態を保存する。新ファイルへの書き込みと検証を終えてから台帳を更新する。同一ID・原資料ハッシュ・抽出版の完了処理は再実行しない。再抽出するときは新しい抽出IDで保存する。

状態は工程別に持つ。取得の状態（pending/ok/no_subtitles/retryable_error/unavailable）と、抽出・確認・結果照合の状態（pending/done/needs_review/not_applicable）を1つの値へ押し込めない。

ネットワーク一時エラーは初期実行後最大2回、30秒・60秒を目安に再試行する。429や認証要求が出たらバッチを止め、停止時刻・再開条件を記録する。無制限リトライやブラウザーCookieの自動持ち出しは行わない。

### 手順7：公式結果と照合

開催日・競馬場・Rを確定し、JRA/NAR等の公式結果と払戻を取得する。現在のプロジェクトのAPI・DBを利用する場合はエンドポイントとデータの出所を実装時に確認する。海外など照合経路が未対応のレースは未照合として残す。

事前予想と判断できるのは、公開時刻が公式発走時刻より前で、動画内容も事前予想のもの。日付しか取れず当日内の前後が判別できない場合は保留する。回顧の「買っていた」という発言は購入申告として保存し、事前公表予想の実績には足さない。

BOX・流し・フォーメーションは券種の順序性、同一馬の重複禁止、重複券の扱いに従い組み合わせへ展開する。表示点数と展開点数が一致しない場合は要確認とする。提案馬券と購入申告、変更前と最終案を分け、同一レースの予想を二重集計しない。

回収率は確認済みの金額・払戻単位がそろう範囲で計算する。不明を0円にしない。一律100円の仮想購入は別集計にする。的中率の分母がレース数か馬券数かを明記し、対象期間・除外数も併記する。

### 手順8：思考方法と変遷をまとめる

レースごとに「条件→判断→馬の評価→買い目への反映→結果・回顧」を並べる。本人の発言と分析者の解釈を分ける。

繰り返しの判断基準は、異なるレースの複数の根拠、成立条件、例外、反例、時期を添えてまとめる。1回だけの発言は単発見解とする。「逆神」等の演出やコメント欄の評判から成績を判定しない。失敗例も同じ形式で残し、結果を知った後の説明を事前の判断力として評価しない。

総括は抽出・確認済みデータから生成する。毎回全字幕をLLMへ送り直さない。年度・券種・理由タグで追跡でき、根拠時刻から原動画へ戻れる形にする。

## 6. 完了の定義と再現性

「全件取得」と「全件検証」を別々に報告する。

- 棚卸し完了：全対象一覧の巡回が終わり、台帳とスナップショットが保存されている。
- 全件処理完了：全台帳行に取得・抽出等の結果または不能理由がある。
- 全件検証完了：対象動画を全編確認し、買い目・理由の漏れと誤りを照合できている。未確認動画が残る場合、この表現は使わない。
- 集計完了：確認済み範囲の成績・思考方法と、未確認範囲・件数が報告されている。

試行による品質確認や買い目箇所だけの確認は、全動画の全編検証とは呼ばない。全編確認が難しい場合は、対象全件を台帳に載せた上で「自動抽出済み・部分検証」と明記する。

再現性は「同じ原資料・固定した版から同じ根拠をたどれる」「再開で重複や欠落が生じない」を必須とする。ネット上の原資料の不変性やLLMの毎回完全同一の出力は保証しない。LLM出力を保存し、訂正は履歴にする。

## 7. 工数の見積もり

試行前に確定日数を出さない。台帳総件数をN、字幕なし件数をMとして、試行の分類別実測値で算出する。

- 取得・整形の見込み時間＝件数×分類別の平均処理時間。
- 音声補完の見込み時間＝字幕なし件数×音声長×実測の処理時間比。
- 人の確認時間＝全編確認の対象総時間＋訂正・照合時間。
- 外部API費用＝実測の動画当たり使用量×対象件数。文字起こしがあれば別計上。

参考計算として、1,500本が平均20分なら総尺は500時間。これはチャンネルの実測値ではない。全編確認を求める場合、この規模の人手作業が発生し得ることを試行時に評価する。

## 8. スキル化への受け渡し

候補名：youtube-keiba-history-analysis。

起動対象：公開競馬チャンネルの過去予想、買い目、判断理由、結果を出典付きで整理する依頼。単一レースの新規予想や動画制作には使わない。

SKILL.mdに置く内容：入力、実行モードの選択、重要なデータ区別、状態保存・再開、完了定義、関連資料へのリンク。詳細スキーマ・抽出指示・確認基準はreferencesへ分ける。

繰り返し処理を担う補助スクリプト候補：一覧収集、字幕収集、字幕整形、JSON検証、進捗更新、買い目展開・結果照合、レポート生成。LLMの実行は利用環境が決まってから接続方法を選ぶ。これらは未実装であり、存在するコマンドとして呼び出さない。

実装順は「5本取得試行→保存形式・再開処理→抽出と確認→20〜30本試行→全件バッチ→結果照合・集計→SKILL.md」。作動していない大量取得手順を先に完成済みスキルとして登録しない。

スキル化前に実証する例：正常字幕、字幕なし、馬名誤認、複数レース、予想変更、画面だけの買い目、金額不明、発走前後不明、中断後再開。同じサンプルの再実行で原資料保全・重複なし・出典追跡を確認する。

次回の着手点：本資料を入力として専用作業ルートを決め、5本の字幕取得試行を実施し、取得可能性と未取得理由を記録する。

## 9. Jev / OpenRouterを組み込む案

ユーザーはOpenRouter契約済み。今回の分類工程の候補としてJevを検討する。契約の存在と、実行環境のAPIキー・利用可能残高・API接続の確認は別事項であり、現時点では有料API試行を実施していない。

### 適合する用途

Jevはテキストから選択肢等の構造化された判断を返すモデル。今回の用途では「競馬関連か」「予想・回顧・理論・一口馬主のどれか」「買い目の明示があるか」等の分類に適合する可能性がある。動画URLを渡して映像・音声を解析する役割や、字幕取得・文字起こし・自由形式の思考方法要約は任せない。[Jevモデル仕様](https://openrouter.ai/typesafe/jev-1.13)

Jevの返す確信度は、そのまま実際の正答率とは扱えない。日本語競馬動画での分類精度は未検証であり、別分野のベンチマークを転用しない。[OpenRouterの分類検証](https://openrouter.ai/blog/insights/jev-vs-claude-opus-5-classification/)

### フロー上の位置

1. 台帳のタイトル・概要をJevへ渡し、本文取得前の仮分類を付ける。
2. 字幕取得後は時刻付き区間をJevへ渡して、予想・買い目・理由等を含む候補区間を分類する。
3. LLMが対象区間から馬名・組み合わせ・金額・理由を抽出する。
4. 音声・画面で確認し、公式結果との照合を行う。

Jevの分類は処理順・確認候補の選択に使う。タイトルだけで「競馬ではない」と判定した動画も台帳から削除せず、全動画対象の要件では本文確認のキューに残す。字幕区間分類で選ばれなかった区間も保存し、抽出漏れを確認する。

### 判定質問の設計案

以下は業務上の質問・ラベル案であり、そのまま送信できるAPIのJSONではない。実装時は最新のDecisions API仕様に合わせてリクエストを作る。通常のチャットAPIから自由文を返させる実装と混同しない。[Jev Labの質問設計例](https://openrouter.ai/labs/jev/compile)

| 質問ID | 入力単位 | 回答候補・定義 |
|---|---|---|
| topic | 動画メタデータまたは本文区間 | keiba：競走馬・レース・馬券等が実質的な話題／other：別の話題／uncertain：根拠不足 |
| content_kind | 動画または本文区間 | prediction：事前評価・予想／review：レース後の検討／theory：一般的判断基準／ownership：一口馬主／other／mixed／uncertain |
| explicit_ticket | 本文区間 | present：具体的な券種・組み合わせ等の提案や購入申告／absent／uncertain。本命名だけでpresentにしない |
| reasoning_present | 本文区間 | present：評価理由・適用条件の説明／absent／uncertain |

動画の分類とレースの事前・事後判定は別にする。predictionと分類されても公開時刻・発走時刻の照合を省略しない。異なる内容が混在する動画を1ラベルだけで切り捨てない。

### 再現可能な比較試行

1. 台帳から予想、回顧、理論、一口馬主、雑談、タイトルが曖昧な動画を含む固定サンプルを選ぶ。最初は20本程度とし、動画IDを保存する。
2. 人が本文を確認して分類と買い目の出現区間を記録する。正解資料が不足する動画は比較対象から分ける。
3. 同じサンプルで「タイトル・概要のみ」「字幕区間あり」のJev判定を保存する。実際の字幕・入力長に対する費用と待ち時間を測る。
4. 競馬動画をotherとする誤り、買い目の区間を見逃す誤り、曖昧な事例を測る。全体正解率だけで採用しない。
5. 質問や確信度の閾値を調整した場合は版を上げる。追加の別サンプルで再確認し、調整に使った動画だけで効果を判断しない。
6. 誤分類を保留・LLM確認に回す運用で、処理時間・費用が減り、重要箇所の見逃しが管理できる場合に採用する。効果が小さければタイトル等の仮分類だけに限定するか、Jev工程を省く。

初期は高確信度でも動画を自動除外しない。判定確信度、低確信度の保留率、見逃し、ラベル別の件数を報告する。確信度の採用閾値は試行で決め、他分野の値を固定でコピーしない。

### 実装条件

- モデルは試行で利用可能性を確認した固定IDを使う。候補はtypesafe/jev-1.13。latestは更新されるため、比較試行で固定版の代わりに使わない。
- 原字幕の区間IDを判定結果に関連付ける。入力資料と範囲、分類質問の版を保存する。
- コンテキスト上限内の区間に分け、複数区間を扱う場合も判定対象のIDを明示する。長い字幕を黙って切り捨てない。
- APIキーは環境変数等から読み、成果物・ログへ値を書かない。残高や接続の確認時も秘密値を表示しない。
- 単価は実行日のモデルページで確認し、実応答の使用量・請求額を記録する。分類費用と抽出LLM・文字起こし費用を分ける。
- API失敗時にotherやabsentへ置き換えず、未判定として再開対象にする。

この追加工程の実装開始点は「台帳・字幕の5本試行」に続く少数のJev分類比較。Jev採用を前提に字幕取得工程を省略しない。
