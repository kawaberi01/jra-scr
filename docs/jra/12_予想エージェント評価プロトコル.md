# 予想エージェント評価プロトコル

## 1. 目的

この文書は、中穴ワイド予想エージェントを「結果に合わせて都度変えるAI」ではなく、検証可能で、改善と悪化を判定できる馬券理論として育てるための評価プロトコルを固定する。

ここで扱う自己学習は、LLMモデル自体の学習ではない。理論ルール、重み、除外条件、買い目生成方針をバージョン管理し、固定された評価手順で比較する運用である。

## 2. ゴール定義

### 2.1 v1 目標

中穴ワイド予想エージェント v1 の目標は、未使用検証期間で以下を同時に満たすことである。

- 軸馬3着内率: 45%以上
- ワイド回収率: 100%以上
- 買い目点数: 1レース最大2点
- 買い目条件: 単勝8倍以上30倍以下の中穴馬を最低1頭含める

この目標は「必ず当てる」ことではなく、以下の性質を持つ買い目理論を作るための初期基準である。

- 軸馬が大崩れしにくい
- 中穴が馬券内に来たときに回収できる
- 大穴依存になりすぎない
- 買い目点数を増やして見かけの的中率を上げない
- 結果に合わせた後出し修正を避ける

### 2.2 成功判定

v1 は validation で改善余地を確認し、holdout で一発評価する。holdout 結果を見た後に v1 のルールを変更してはならない。

holdout で目標未達の場合、v1 は失敗または追加検証扱いとし、修正版は v2 として別バージョンにする。

## 3. データソース

評価では以下を使用する。

- JRA既存DBの過去走データ
- netkeiba API の `race_result`
- netkeiba API の `odds_view`

### 3.1 JRA既存DB

JRA既存DBは、予想時点より前の過去走特徴量を作るために使う。

主な使用項目:

- race_id
- race_date
- course
- race_no
- race_name
- surface
- distance
- horse_no
- horse_name
- jockey
- trainer
- weight_carried
- rank

### 3.2 netkeiba race_result

`/netkeiba/races/{race_id}/result` は、対象レースの結果照合と確定情報の補完に使う。

主な使用項目:

- 着順
- 馬番
- 馬名
- 単勝オッズ
- 人気
- 馬体重
- 馬体重増減
- 上がり
- 払戻
- 天候
- 馬場状態

Prediction Agent に対象レースの結果を渡してはならない。`race_result` は評価フェーズでのみ使用する。

### 3.3 netkeiba odds_view

`/netkeiba/races/{race_id}/odds` は、予想した買い目のワイドオッズ確認に使う。

原則として、全組み合わせを保存するのではなく、Prediction Agent が出した買い目だけを取得する。

例:

```text
GET /netkeiba/races/{race_id}/odds?bet_type=wide&combination={axis},{middle}
```

ワイド、馬連、3連複などの順不同券種では、組み合わせ順序は評価上同一として扱う。

## 4. race_id の扱い

JRA既存DBの race_id と netkeiba の race_id は直接一致しない。

例:

```text
JRA既存DB: 202606280301
netkeiba: 202603020201
```

評価実行前に、必ず次のいずれかを固定する。

- JRA race_id から netkeiba race_id への変換ルール
- JRA race_id と netkeiba race_id の対応表

変換または対応表が曖昧なレースは評価対象から除外し、除外理由を記録する。

## 5. 期間分割

### 5.1 基本分割

```text
train:
2025-01-05 から 2025-09-30

validation:
2025-10-01 から 2025-12-31

holdout:
2026-01-01 から 2026-06-28
```

### 5.2 各期間の役割

| 期間 | 役割 | ルール変更 |
|---|---|---|
| train | 特徴量設計、候補ルール作成 | 可 |
| validation | バージョン比較、採用候補選定 | 可。ただし変更は新バージョンにする |
| holdout | 未使用期間での最終確認 | 不可 |

### 5.3 汚染済みデータの扱い

2026-06-28 福島は小検証で結果を見ているため、holdout の最終判定から除外するか、汚染済み参考ログとして扱う。

汚染済みレースを使ってルールを変更してはならない。

## 6. v1 ベースラインルール

### 6.1 入力

Prediction Agent が使用できるのは、対象レースより前に確定している情報のみとする。

使用可:

- 対象レースより前の過去走
- 対象レースの出走馬情報
- 対象レースの発走前に取得できる単勝オッズ、人気、馬体重
- 発走前の天候、馬場状態

使用不可:

- 対象レースの着順
- 対象レースの払戻
- 対象レースの上がり
- 対象レースのレース後コメント
- 結果を含む記事

現時点のDBでは発走前オッズの過去保存が限定的なため、過去検証では netkeiba `race_result` の確定単勝オッズを中穴レンジ判定に使う。ただし、これは「過去検証用の代替」と明記し、リアル運用時は発走前スナップショットを使う。

### 6.2 軸馬選定

v1 の軸馬は、対象レースより前の過去走だけから作ったスコアが最も高い馬とする。

初期スコアの構成要素:

- 通算3着内率
- 直近5走3着内率
- 平均着順
- 同芝ダート3着内率
- 近距離条件3着内率
- 出走履歴数による小さな補正

対象レース当日の結果、払戻、上がりはスコアに使わない。

### 6.3 中穴相手選定

相手馬は、以下を満たす馬から最大2頭選ぶ。

- 軸馬以外
- 単勝オッズ8倍以上30倍以下
- 過去走スコア上位

該当馬が0頭の場合、そのレースは購入なしとする。

### 6.4 買い目

券種はワイドのみとする。

```text
軸 - 中穴1
軸 - 中穴2
```

1点100円で固定する。1レース最大2点、最大購入額200円とする。

### 6.5 評価

的中判定は deterministic code で行う。LLMに的中判定をさせない。

払戻は `race_result.payouts` を正とし、買い目のワイドオッズ確認が必要な場合だけ `odds_view` を参照する。

## 7. 評価指標

### 7.1 primary metrics

| 指標 | 定義 |
|---|---|
| ワイド回収率 | 払戻合計 ÷ 購入額合計 |
| 軸馬3着内率 | 軸馬が3着以内に入ったレース数 ÷ 評価レース数 |

### 7.2 secondary metrics

| 指標 | 定義 |
|---|---|
| ワイド的中率 | 的中買い目数 ÷ 購入買い目数 |
| 中穴馬3着内率 | 選んだ中穴馬が3着以内に入った割合 |
| 1レース平均購入点数 | 購入買い目数 ÷ 評価レース数 |
| 見送り率 | 購入なしレース数 ÷ 評価対象レース数 |
| 除外率 | 除外レース数 ÷ 候補レース数 |
| 最大払戻依存度 | 最大払戻1件を除いた回収率との差 |
| 単勝オッズ帯別成績 | 軸馬、中穴馬の単勝オッズ帯ごとの成績 |
| 人気帯別成績 | 軸馬、中穴馬の人気帯ごとの成績 |

### 7.3 最大払戻依存度

回収率が高くても、1件の大きな払戻に依存している場合は理論として弱い可能性がある。

そのため、以下を必ず併記する。

```text
全払戻込み回収率
最大払戻1件を除いた回収率
最大払戻3件を除いた回収率
```

## 8. 除外条件

除外条件は評価実行前に固定する。結果を見てから除外してはならない。

v1 の除外条件:

- JRA race_id と netkeiba race_id の対応が不明
- netkeiba `race_result` が取得できない
- 結果または払戻が欠落している
- 出走馬との馬名照合が一定割合未満
- 過去走が2走以上ある候補馬が6頭未満
- 軸候補を決定できない

v1 では新馬戦、2歳戦、障害戦を機械的には除外しない。ただし、履歴不足条件により自然に除外されることがある。

将来バージョンで新馬戦、2歳戦、障害戦を除外する場合は、v2 以降の明示的なルール変更として扱う。

## 9. 改善イテレーション

### 9.1 基本手順

```text
1. 評価プロトコルを固定する
2. v1 ルールを固定する
3. validation で評価する
4. 結果を分析する
5. 改善案を1つだけ作る
6. 改善案を v2 として固定する
7. v1 と v2 を同じ validation 条件で比較する
8. 採用候補を1つだけ選ぶ
9. holdout で一発評価する
10. holdout 結果を見て同じバージョンを変更しない
```

### 9.2 バージョン管理

ルール変更は必ずバージョンを分ける。

例:

| バージョン | 変更内容 |
|---|---|
| v1 | 過去走スコア最大馬を軸にする初期ルール |
| v2 | 軸馬に単勝人気条件を追加 |
| v3 | 中穴レンジを8から30倍から10から30倍に変更 |
| v4 | 履歴不足レースの除外条件を強化 |
| v5 | ワイドオッズ下限を追加 |

### 9.3 変更は1回に1論点

1つのバージョンで複数の大きな変更を同時に入れない。

悪い例:

```text
v2 で軸条件、中穴レンジ、除外条件、買い目点数を同時に変える
```

良い例:

```text
v2 では軸条件だけ変える
v3 では中穴レンジだけ変える
```

### 9.4 採用条件

新バージョンは、少なくとも以下を確認してから採用候補にする。

- primary metrics が改善または維持されている
- 最大払戻依存度が悪化していない
- 買い目点数が増えていない
- 除外率が不自然に高くなっていない
- 中穴条件を満たしている
- 大穴依存が強まっていない

回収率だけを理由に採用してはならない。

## 10. やってはいけないこと

以下は禁止する。

- 結果を見てから対象レースに合わせてルールを変える
- 外れたレースを後から除外する
- 当たったレースに都合のよい条件を追加する
- holdout の結果を見て同じバージョンを修正する
- 小サンプルの一発高配当に引っ張られて昇格する
- 買い目点数を増やして的中率だけを上げる
- 単勝50倍超の大穴を主役にする
- 予想、結果照合、改善案作成を1つのLLM判断に混ぜる
- LLMに的中判定を任せる
- race_result 由来の結果情報を Prediction Agent に渡す
- 汚染済み参考ログを holdout の根拠にする

## 12. v1 実行前チェックリスト

v1 を validation で実行する前に、以下を確認する。

- 評価期間が固定されている
- JRA race_id と netkeiba race_id の変換または対応表が固定されている
- 除外条件が固定されている
- 買い目条件が固定されている
- Prediction Agent に結果情報が渡らない
- 的中判定が deterministic code である
- 最大払戻依存度を出す
- 実行後に v1 のルールを書き換えない

## 13. 次の作業

次に行うべき作業は、v1 ベースラインを validation 期間で一括評価することである。

対象:

```text
2025-10-01 から 2025-12-31
```

実行前に必要なもの:

- JRA race_id から netkeiba race_id への対応表
- netkeiba API のアクセス間隔設定
- 評価結果保存先
- 除外理由の記録形式

この validation 結果を見るまでは、v2 のルール変更を始めない。
