# 010-JRA発走前ライブシャドー記録実装仕様書

## 0. 最初に読む要約

- 対象機能: JRA発走前ライブシャドー記録
- 改修目的: スカウト時の判断材料と判断結果を再現可能な1観測として永続化する。
- 現行仕様の要点: スカウトは必要なデータを生成済みだが、要約しか保存していない。
- 最重要注意点: 保存する判断は常に`shadow_only`かつ`tickets=[]`とする。

## 1. 変更後仕様

### 入力

- スカウトrun ID、対象レース、単勝オッズ、公開材料順位、履歴モデル順位。
- artifactの`model_version`、`created_at`、`trained_through`。
- 判断の`policy_version`、component status。

### 出力

- `JraLiveShadowObservation`。
- `GET /jra/races/{race_id}/live-shadow-observations`で観測時刻の新しい順にページングして返す。

### 正常系

1. 未発走レースの予想bundle取得に成功する。
2. 単勝判断を生成し、スカウトgradeを算出する。
3. 判断の元statusを`source_status`へ残した上で、保存用判断を`shadow_only`、`tickets=[]`へ正規化する。
4. オッズの`fetched_at`を観測時刻として、入力と判断を1payloadへまとめる。
5. スカウトrun・entry・観測を同一DB transactionで保存する。

### 異常系

- 開催座標不足、発走済み、モデル利用不可、bundle取得失敗のレースは観測を作らない。
- 観測がない既知レースは空pageを返す。
- 未知の`race_id`は既存参照APIと同様に`LookupError`とする。

### 副作用

- `jra_live_shadow_observations`へrun・race単位で保存する。
- 同じ`run_id`・`race_id`の再保存は同一観測の更新とし、別runの観測は保持する。

## 2. データ契約

`JraLiveShadowObservation`は次を保持する。

- 識別: `observation_id`、`run_id`、`race_id`、`race_date`、`course`、`race_no`
- 時刻: `observed_at`
- モデル: `model_version`、`model_created_at`、`trained_through`
- policy: `policy_version`、`decision_status`、`ticket_status`
- 観測payload: `odds`、`materials_ranking`、`history_ranking`、`decision`、`component_status`

DBは検索列と`payload_json`を保持し、`unique(run_id, race_id)`および`(race_id, observed_at)` indexを持つ。

## 6. テスト観点

- shadow正規化で元statusを保持し、ticketが必ず空になる。
- Storeが別runの複数観測を保持し、新しい順・ページングで返す。
- 同一run・raceの再保存で重複しない。
- スカウト結果と観測が同一保存処理で永続化される。
- APIが型付きJSON、空配列、validationを返す。
- 既存スカウト・snapshot・通常戦EVの回帰がない。

## 7. 対象外

- 閾値・モデル係数の変更。
- 確定結果との自動採点。
- 定刻起動、odds snapshot履歴化、DB index最適化。
