# JRA開催日自動収集仕様

作成日: 2026-10-12

## 目的と現状

祝日月曜・振替開催を曜日に依存せず収集する。現行の Windows タスクは土曜・日曜9:00のみ。収集本体は指定日の開催一覧を取得するため、曜日制限はない。

既存タスクは待機中。10/10・10/11の終了コードは非0だが当該日のログがなく、タスク履歴も無効のため過去の失敗原因は断定できない。Windows PowerShell 5.1で `ErrorActionPreference=Stop` と `rtk ... 2>&1` を組み合わせると、RTKの警告だけでNativeCommandErrorになり中断することを再現した。Notionの既存RTK移行記録も参照した。

## 変更契約

- 毎日9:00（Windowsの日本時間設定）に単一タスク `JRA-SRB-Odds-Daily` を起動する。祝日一覧は作らず、既存JraServiceの公式開催一覧取得を再利用する。
- 開催なしは `no_meetings` と収集数0を記録し終了コード0。開催情報取得例外は正常な非開催扱いにせず非0終了。対象開催があるのに有効な発走時刻が1件もない場合も非0終了。
- 起動スクリプトは既存の当日対象を維持し、日本時間で日付を決める。遅れて起動しても取得期限を過ぎた時点は既存処理でスキップする。過去時点の埋め合わせはしない。
- 単勝・馬連・ワイドは30/10/2分前、3連複は10/2分前。間隔1秒、許容遅延120秒を維持する。保存先は共通backend設定に従う（SQL Server移行後は `jra_unified.api_runtime`）。互換用DBパス引数は維持する。
- 2026-10-24改訂: 日次起動の固定上限432を撤去する。上限未指定時は、選択開催の各取得時点について出馬表1回＋設定券種数を足し上げて有限の上限を自動算出する。通常2場24Rは336回、3場36Rは504回。既存保存・期限超過によるスキップがあっても上限は予定全体の値とする。失敗した取得試行も上限を消費し、再試行は増やさない。
- CLIの明示上限は維持し、負数は拒否する。未処理予定がある状態で上限に達した場合、理由 `request_limit_reached`、上限、取得試行数、未処理オッズ予定件数をログに出し、終了コード1を返す。ちょうど上限で全件完了した場合は成功とする。未処理件数は未確認の将来時点も含み、DB欠落の確定件数とは区別する。DryRunは予定上限だけを算出し、上限打切り扱いにしない。
- uvの実行パスを解決して直接起動する。RTKの警告による中断を防ぎ、対話環境の古いPATHへの依存を減らす。新しいライブラリは追加しない。
- 起動前からUTF-8ログを作成する。実行単位で標準出力・標準エラー・起動/終了記録を分け、終了コードをタスクへ返す。
- タスクはIgnoreNew。同じ起動スクリプトの手動実行も排他ロックで二重収集を防ぐ。直接CLIを起動する運用はロック対象外。
- 登録用スクリプトは旧タスクのXMLをバックアップし、新しい日次タスクの登録を確認してから旧週末タスクを無効にする。実行中タスクがあれば切替を中止する。旧タスクを削除しない。
- Windows登録まで適用し、事前確認が通った場合は本日の残り時点も日次タスクから収集開始する。

## 対象外と制約

予想・購入ロジック、公開指数/調教/持ち時計の追加収集、DBスキーマ、既存履歴の再取得は対象外。この変更は出馬表とオッズ時系列を収集するためのもの。quickスカウトのnot_loaded状態は別仕様。

ログオン方式は既存タスク同様Interactive/Limited。PC停止・未ログオン時は収集できず、StartWhenAvailableによる遅延起動でも失った過去時点は復元できない。スリープ解除やパスワード保存は追加しない。

## 確認方法

- 既存収集テストと、月曜開催・非開催・発走時刻欠落・開催取得失敗の回帰確認。
- Windows PowerShell 5.1構文解析、当日のDryRunで月曜2場24レースのスケジュールを確認。DryRunは出馬表/オッズを取得せず保存しない（DB初期化/開催一覧キャッシュは既存CLIの挙動）。
- 登録後の日次トリガー・実行パス・旧タスク無効化を再取得して確認。
- 本日タスク開始後、起動ログと実行中状態を確認。全日収集の完了確認は本日の最終時点後に行う。
