# 005-南関東公式オッズAPI現行仕様整理

## 1. 既存API構成
- FastAPIの入口は `src/jra_srb/app.py` に集約されている。
- JRA公式取得は `JraService` と `HttpProvider` をアプリ起動時に構築し、API endpointからserviceを呼ぶ。
- netkeiba取得は `NetkeibaService` と `NetkeibaHttpProvider` をJRA公式とは別serviceとして追加している。
- オッズレスポンスは共通の `RaceOdds` / `OddsEntry` を使う。
- `RaceOdds` は単一券種の場合 `bet_type` と `entries`、複数券種の場合 `odds: dict[str, list[OddsEntry]]` を返せる。

## 2. 既存のJRA公式オッズ取得
- JRA公式は開催一覧からオッズ入口を解決し、券種別に上流ページを追加取得する。
- 対応券種は `win`, `quinella`, `wide`, `exacta`, `trio`, `trifecta`。
- 単勝・複勝は `parse_jra_win_place_odds`、2連系/3連複は `parse_jra_table_odds`、三連単は `parse_jra_trifecta_odds` で解析している。
- キャッシュTTLは単一JRAオッズで30秒、bundleで45秒。

## 3. 既存のnetkeibaオッズ取得
- netkeibaはJRA公式とは別prefix `/netkeiba` に分離されている。
- `race_id` はJRAと同じ12桁を受けるが、provider/service/extractorはJRA公式とは独立している。
- 南関東公式もこの分離パターンに合わせ、JRA公式serviceへ押し込まず独立serviceを追加するのが既存構成に合う。

## 4. 南関東公式サイトのURL構造
- 開催一覧:
  - `/program/{meeting_id}.do`
  - 例: `20260704190405`
- 出走表:
  - `/uma_shosai/{race_id}.do`
  - 例: `2026070419040501`
- 通常オッズ:
  - `/odds/{race_id}{odds_page_code}.do#odds`
- 人気順オッズ:
  - `/odds_nin/{race_id}{odds_page_code}.do#odds`
- 結果:
  - `/result/{race_id}.do`
- 開催全体払戻:
  - `/repay/{meeting_id}.do`

## 5. 南関東ID仕様
- `meeting_id = YYYYMMDD + place_code + meeting_round + meeting_day`
  - 例: `20260704190405`
  - `YYYYMMDD`: 開催日
  - `place_code`: 南関東場コード
  - `meeting_round`: 第N回
  - `meeting_day`: 第N日
- `race_id = meeting_id + race_no`
  - 例: `2026070419040501`
- 場コード:
  - `18`: 浦和
  - `19`: 船橋
  - `20`: 大井
  - `21`: 川崎
- 場コードはURL実例と南関東4場の並びからの実装仮説。fixtureで4場分を追加して固定する。

## 6. オッズページコード
| コード | ページ | API券種 |
| --- | --- | --- |
| `01` | 単勝・複勝・枠複・枠単 | `win`, `place`, `bracket_quinella`, `bracket_exacta` |
| `04` | 馬複・ワイド | `quinella`, `wide` |
| `03` | 馬単 | `exacta` |
| `09` | 三連複 | `trio` |
| `08` | 三連単 | `trifecta` |

## 7. 実取得で確認した状態差分
- 2026-07-04 船橋1RのオッズページはGETで取得でき、HTML内にオッズ表が含まれていた。
- 2026-07-06 川崎1Rの出走表は取得できたが、オッズURLは404だった。
- 発売前404は、ネットワーク障害ではなくページ未生成の可能性が高い。
- 結果後のオッズページには「最終オッズ」「最終確定票数」が表示される。
- 小頭数や券種条件により「発売なし」が表示される券種がある。

## 8. オッズテーブルの解析パターン
- `01`:
  - 馬一覧テーブルから単勝・複勝を行単位で抽出する。
  - 複勝は `min-max` 形式を `odds_min`, `odds_max` へ分ける。
  - 枠複/枠単は発売なしになる場合があるため、初期実装では空配列または対象外にできる。
- `04`:
  - 馬複とワイドが同一ページ内の別テーブルとして出る。
  - どちらも2頭組み合わせとオッズを抽出する。
- `03`:
  - 馬単は行列型。
  - 同一馬など無効組み合わせは `−` または `－` になるため除外する。
- `09`:
  - 三連複は先頭2頭ペアごとのブロック表。
  - 見出しのペアと行側の3頭目を組み合わせる。
- `08`:
  - 三連単は1着-2着ペアごとのブロック表。
  - 見出しの2頭と行側の3頭目を組み合わせる。
- `odds_nin`:
  - 人気順リスト型。
  - 通常取得の補助、または人気順APIを別途追加する場合に使う。

## 9. 実装上の前提
- 公式HTMLを短TTLで再取得する方式でリアルタイム相当とする。
- 内部JSON APIは前提にしない。
- JavaScript実行は不要。
- Shift_JIS decodeをproviderで扱う。
- 既存 `RaceOdds` / `OddsEntry` を流用する。
