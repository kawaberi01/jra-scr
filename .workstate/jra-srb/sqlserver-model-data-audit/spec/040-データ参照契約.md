移送データ表には`__migration_source_snapshot_id=<固定ID>`を指定する。ops台帳とrace_identity_mapは固有のsource_snapshot_id/source_database_id等で版を解決し、存在しないmigration列を一律に付けない。JOINは版と業務キー、必要なhorizon/marketを全て含める。row SHAと入力全列digestを両方記録する。既存row SHAを実内容の代わりに信用しない。

最低限の抽出順は、(1)対象期間のracesキーを月別取得して候補集合を固定、(2)同じ版のfeatures/asof/entries/payoutsをレースキーで分割取得、(3)labelsを下記例外routeで1回走査して対象キーのOutcomeだけを保持、(4)メモリで1対1対応と適格条件を評価。racesへ市場明細を直接多重JOINして行を増やさない。値はparameter、raceキー集合は最大500件でdriverのparameter制限以下にする。scoreは(3)とpayouts取得を省く。

M0は各大表の既存index key列とSQL型を読み、snapshot/業務キーまたはcomputed hash索引を利用できるquery_idと条件列・parameter型を固定する。hash索引を使う場合は元キー値の完全一致条件も併記する。rawは本文hash索引＋元sha、parsedは観測hash索引＋元業務キーで候補を絞る。巨大表の全scan後にPython filterするrouteは拒否し当該profileをblocked_contractにする。既存索引で成立しなければ索引追加で迂回しない。

**labelsだけの有界例外**: 現inventoryではrace_key索引が無く、`UX(snapshot,__migration_source_rowid)`がある。全1,161,480行（観測値）を500レースごと再走査せず、固定snapshotだけを`TOP(?) ... WHERE __migration_source_snapshot_id=? AND __migration_source_rowid>? ORDER BY __migration_source_rowid`で1回keyset走査する。初回はrowid下限条件なし、1chunk最大10,000行。rowidのNULL/重複/型不一致は停止し、他routeへ自動fallbackしない。候補キー以外はメモリ保持せずstream digestだけ計算する。全snapshot stream digestと採用入力digestを分け、scan行数上限1,500,000（設定可、上限変更は明示）と時間/メモリ上限を検査する。chunked_unprovenの場合のみ2巡して照合。raw/parsed等の巨大表にはこの例外を適用しない。

max_label_scan_rowsは**各巡**の上限。既定は各巡150万行・最大2巡・合計最大300万行（設定値×巡数）。月/レースbatchごとにこの予算を再発行しない。

## 3. M1の利用条件（score入力と学習・評価を分離）

- 共通の予測入力条件はhorizon=T30。生成済みfeaturesのqualityは`research_only_final_SE_identity_mapping_unverified`を既知の研究用状態として認め、strictをfalseにする。未知状態は除外。scoreはlabels/payout/status=finalを要求せず、結果取得も行わない。
- O1/O2ともselection_status=selected、同一parser契約。必要content SHAとfeaturesのsource_o1/o2_sha256が一致すること。cutoffも一致し、矛盾はrace全体を除外。
- 発表時刻は分単位なら秒00を補いtimezone付きdatetimeへ変換し、各announced_at<=cutoffを確認。変換不可・timezoneなしは除外。保存値は更新しない。予定発走時刻が歴史的に未証明な点は残る。
- score入力はO1_numeric_set=features_set=entries_rosterを要求。学習・評価ではさらにlabel_setも等しく、history.races.status=finalであることを追加する。余剰/欠落が1頭でもあれば馬を落として続けずrace全体を除外。active roster不明・重複・無根拠なmissing horse削除は不可。馬番は数値検査後01形式へ正規化、範囲と重複を確認。
- M1はO1全有効馬、O2のそのロスター内の全n(n-1)/2組を要求。O1>=5頭、O2完全、オッズはfiniteかつ>=1。O2 pairは無向の馬番昇順へ正規化し、重複・自己pairはrace除外。ロスター外pairは市場計算から除き件数を記録する。O2分母はO1ロスター内の数値pairのみとし、片馬周辺確率=sum(1/pair_odds)/(2*sum_all_pairs(1/pair_odds))、O1 share=(1/win_odds)/sum_all_horses(1/win_odds)、比率=log(O2周辺確率/O1 share)。featuresの3市場値をentries_jsonから再計算して相対/絶対誤差1e-7以内で照合し、丸め仕様を契約へ記録。旧cross_poolと分母集合が違う場合があり新profileの定義として扱う。
- 全8/9特徴がfinite、23マスクが生成定義と一致。正常rank・正常精算が揃う条件は学習・評価だけに適用する。例外精算は共通精算器で検証するが、M1の学習母集団を無理に広げない。score時はOutcomeBundleの有無・内容で採否/scoreを変えない。
- 学習・評価ではhistory.payoutsのwin/published/payout_yen>0からselection_rawの2桁馬番と金額を読む。labels.hr_sha256と一致、rank=1集合=HR published勝馬集合=official_win_settlement=1集合を検査。0/1フラグを金額に使わない。同じ馬番の重複slotや不正selection_rawはrace除外、同着は異なる馬番の個別金額を保持する。M0はpayout_rawの9桁ASCII数字を整数化してpayout_yenと少数正常/同着例で照合し、生成元のHR保存定義（005参照）を根拠とする。例が対象期間に無ければ固定版内の別キーを使ってよい。raw本文解凍/HR直接照合はM2で追加検証し、M1のraw権限/codec依存を増やさない。
- market/basic/crossの対象race/horse集合を一度確定し共有。O1だけの広いbaselineのカバー率は別reportとしてのみ表示し、モデル優劣の比較へ使わない。

## 4. runtime receipt契約

`write_receipts`はrequest_sha256、operation、race_id、payload_json、received_at_utcを利用する。M1では不要。後続で次を満たした場合のみ有効にする。

- race_card/odds/race_resultのoperationごとに、received_at_utc<=固定knowledge_cutoffで選択。レース日/馬/券種/観測時点/sourceもpayloadで検査する。受信時刻、provider fetched_at、公表時刻、判断締切を別フィールドで持つ。
- 同時刻の異なる本文に訂正順の証拠がなければambiguous_revisionとして除外。request_sha256順は表示の決定性にのみ使い、真の新旧順とみなさない。
- 予測入力は公表時刻だけでなく受領時刻も判断時点以前である必要がある。事後に受け取った過去オッズをstrict_liveとして採用しない。
- race_resultは同じreceipt.payload_jsonから親・明細・払戻を一束で復元。現在業務表を別queryで取って混ぜない。receiptのpayload schema版が変わればadapter版を分ける。
- seed時点以前はlive snapshot34の同race_id・同sourceから完全束を取得する。capture時点以降に既知だった固定版という扱いに限定し、古いfetched_atから当時受領済みと推定しない。baselineが当該cutoff後なら採用不可。
- snapshot31/34とruntimeの重複はpolicyの明示whole-bundle優先順で選択。足りない結果やオッズを別sourceの行で埋めない。
- receipt開始前・対象外の更新は復元不可の場合がある。必要な版が無い時はreplay_unavailableとする。new runtime IDのID mapが未登録なら未解決扱い。

## 5. ID対応

`history.race_identity_map`のsource_snapshot_id/source_relation/source_original_id、jv_race_key_12/full_16、api_race_id、unified_race_id、mapping_status、evidence_jsonを用いる。各sourceの固定版と検証済みmappingを解決しunified_race_idで接続する。日付・場コード・race_noと1対1/逆向き一意も照合する。

historyの12桁とAPIの12桁は同じ形式と仮定しない。先頭切出し・文字列位置だけの変換・同じ馬名の同一馬扱いをしない。未登録の新raceはSQL上の業務属性を使った一意検査の候補をcoverageへ出せるが、検証状態を勝手にverifiedへ昇格しない。DBのID mapへ書込まない。

## 6. raw再解析と履歴再計算

通常は既存featuresとasof.entries_jsonを使う。新定義に必要な時だけ`raw.master_contents`のcodec/compressed_payload/raw_length/sha256を使い、同じ内容SHAへ固定して解凍・長さ・本文SHAを検証する。NASファイルへfallbackしない。

raw版はnas-master等のsource台帳で解決して具体ID固定。snapshot番号29等を全環境へhardcodeしない。content_sha256とmaster sha256の一致経路は少数本文で検証して有効化する。parsed_observations.source_sha256とcontent_sha256は未証明のため結合禁止。raw_record_idとparser_versionの結合も出典版と型を含めて検証する。

### M2内容検証の明示別契約

`sql_content_verified_compat_v1` の追加は上記の未証明結合を解禁するものではない。parsedのsource_sha256をmasterのsha256へ内容検証付きで接続し、asof31のcontent_sha256との同一性を名前だけで推定しない。通常の旧互換materializerやstrictライブの受入をこのcapability単独で通さない。

- M2専用preflightで、各source_keyと指定snapshotのverified状態、DB/reader権限、raw/market schemaのALTER/CONTROL不許可、必要objectのSELECTとDML/DDL不許可、列型・computed式・既存索引のkey順と有効性を確認する。定義非可視を正常としない。管理者接続・GRANT・DDLで迂回しない。
- 観測候補は固定parsed版＋race hash＋元race値のbyte完全一致、DataSpec/parserで有界抽出する。明細は固定版＋observation hash＋元raw_record_id/parserのbyte完全一致。本文は固定master版＋本文SHA hash＋元SHAのbyte完全一致を使う。
- cutoffの判定はtimezone付きUTCで行い、同時刻の異内容は訂正順の証拠がなければ競合として拒否する。候補全体を確認せず採用候補だけで競合なしとしない。
- 採用する全本文のcodec・圧縮長・展開長・SHA・種別・race・発表時刻を検証し、利用券種の全parsed明細を既存parserで再解析比較する。fullkey・make_date・頭数・発売flags・票数等を使う場合は再解析値のみを採用するか全使用列を一致照合する。
- レース当り観測数、明細数、圧縮byte、全体memoryと二巡読取の上限を設定し、超過・不一致・未知codecは依存処理停止。本文/SQL行/全特徴量を永続保存しない。
- 旧metadata lookupの索引不足は未解消のまま記録する。旧checkpoint/cutoff/card/PastForm・ID map・共通精算の受入は別途必要であり、この検証成功をM2全体完了へ読み替えない。

履歴再計算は予測対象日より前の確定済み結果だけを使い、horse_id/horse_name、履歴開始日、頭数定義、取消/同着処理をFeatureContractに含める。既存23マスクを外すには利用可能時刻の証拠またはretrospective専用profileが必要。過去訂正があれば影響する後続レースを計算対象に含め、DBへ生成物を保存しない。

## 7. 権限・整合性・再現quality

preflightは全研究用の単一reader設定から、該当profileで必要な表のSELECTとINSERT/UPDATE/DELETE/ALTER/CONTROL等を既存メタデータ/権限関数で検査する。jra_readerがapi_runtimeも読めるかは未確認。API loginとの資格情報併用や管理者への昇格はしない。権限不足時は必要schema/表/権限だけを別担当向けreportへ出す。

実効権限の拒否対象はsysadmin、db_owner/db_ddladmin/db_datawriter、DATABASE scopeのCONTROL/ALTER ANY SCHEMA/CREATE TABLE、必要schemaのALTER/CONTROL、対象objectのINSERT/UPDATE/DELETE/ALTER/CONTROL。固定SELECTのHAS_PERMS_BY_NAME/IS_ROLEMEMBER/IS_SRVROLEMEMBERと対象SELECT成功で検査し、書込み試験をしない。NULLやmetadata非可視は0扱いせず検査不能として3で停止する。

SQL isolationはDB設定を読取確認する。SNAPSHOT有効なら一つのread-only transaction内で入力を読み、学習前にrollback/close。NOLOCK・READ UNCOMMITTED禁止。snapshot無効なら長時間ロックや設定変更で解決せず、frozen版限定・短いREAD COMMITTED抽出でread_consistency=chunked_unprovenと明示する。この場合は候補集合と入力に使う全キー/全列を2回読取り、各canonical stream digestを比較する。差があれば全入力を破棄する（既存row SHAだけの再読取は禁止）。2回分の読取も上限/timeoutを守り、負担を理由に検査を省略しない。前後一致だけではABAや全表同時整合を証明しない。strict consistency要求profileでは4で停止する。

qualityは別軸: `availability={research_only,strict_live}`、`read_consistency={snapshot_transaction,chunked_unproven}`、`replayability={version_addressable,content_match_only,unavailable}`。snapshot_idの存在だけでphysical immutableとはしない。行SHAだけでなく正規化した全利用列のstream digestを取り、replay時一致して初めて再読取一致と報告する。元版消失/修正時は復元不能とする。

正規化digestは契約版付きcanonical JSONL: 業務キー順、固定列順、UTF-8、timezone UTC、null維持、finite数値のみ、oddsは元の整数単位または正規化decimal文字列、feature floatはround-trip表現、改行LF。同じキーの二重出現はhash前に拒否。入力キーのdigestと内容digestを分け、欠損・mask・source/版も内容へ含める。

## 8. coverageと除外コード

最小コード: missing_race/card/result/payout/O1/O2/features、not_sold、outside_history、unresolved_id、duplicate_key、version_conflict、ambiguous_revision、invalid_timestamp、after_cutoff、unproven_live_time、unexpected_mask/null、roster_mismatch、settlement_unknown、unsupported_market、source_changed、memory_limit、permission_denied。候補全体について採用+除外が一致し、複数理由の件数を単純合算しない。

独立した全開催母集団がSQL内に確認できない場合、coverage_basis=stored_racesとし、全JRA網羅率と呼ばない。全開催完備を要求するprofileでは母集団未確認をblockerにする。除外によって当初の要求が満たせないprofileを実装済みだけで完了扱いしない。
