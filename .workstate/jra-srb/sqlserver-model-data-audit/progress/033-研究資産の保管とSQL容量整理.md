# 研究資産の保管とSQL容量整理

確認日: 2026-10-17。利用者の方針: 最優先の予想家由来研究と機械学習系V91〜V111以外は、過去研究の結果・結論を残せばよく、全データ再整形・再検証は不要。時間と保存量を増やさず、SQL Serverにある不要な研究データも削減したい。

## 1. 整理方針

- 終了研究は、目的・方法・条件・対象期間・結果・結論・主要な注意点・元記録への参照を保管する。棚卸し029/030と既存報告を使い、原データや全特徴量をもう一式作らない。
- 終了研究の全モデル再学習、全候補/全fold再実行、旧入力の全量再整形、SQL専用化は現在の必須作業から外す。
- 最優先2系統で使う共通の過去成績・原本・オッズ・結果/払戻は、旧研究でも使ったという理由で不要とはしない。
- 削減対象は、必要な研究/予想から参照されず、用途が終了し、保管すべき結果記録を失わないと確認できた重複版・派生表・中間物。現段階で削除確定した表/行はない。
- 今回はmetadata/容量/移送元/依存の読取だけ。DELETE/TRUNCATE/DROP/圧縮/SHRINK/バックアップ作成/元データexportは行っていない。

## 3. 「研究データを増やしてしまった」ことの確認

- 大容量表の台帳上の出所はsource28（jvlink-current）、29（nas-master-20261005）、30（odds-parsed-current）、31（prediction-full-20261008）。既存移送データであり、直近のモデル実行のたびにSQLへ全量を追加する構成ではない。
- 現研究CLIはSELECTを入力とし、モデル・評価等はローカルrun成果物へ保存する設計。直近の明示DB補修は5表の定義参照権限とID map3,455件の4列更新で、原本/特徴量を新規全量投入する処理ではなかった。
- API切替ではapi_runtimeへのseedが別途あった。これは運用保存先の切替用であり、終了研究の実験用コピーと一括して削除しない。
- prediction schema全体8.75GiBの大半は特徴表8.72GiB。過去予想・研究の結論/評価記録そのものを消しても、大容量の削減には直結しない。残すべき記録を先に消さない。

## 4. これから行う確認は限定的な削除判定

1. 優先2系統＋当日予想/保存が必要なテーブル・列・source版を対応付ける（spec090のP0と共通）。既存の容量/移送metadataを使い、全原本を最初から走査しない。
2. 上表の候補について「参照なし」「別の正本で同じ情報を保持」「再生成不要/可能」「残す結論・運用記録を失わない」を確認する。これは過去モデルの成績再検証とは別。
3. 削除計画を表/版/条件・対象件数・容量見込み・影響するview/reader/来歴・戻し方まで具体化する。元の保全指示と今回の不要データ整理指示の適用範囲を明記する。
4. 対象を利用者が確認できる状態にしてから削除を実施する。必要データを失う不可逆操作を「不要なはず」という推測で進めない。
5. 削除後のDB内部空きと、OS/Docker上で実際に戻った容量を区別する。ファイルを小さくする操作が必要な場合だけ、削減後に別途検討する。

SQL Serverはデータを削除しても、割り当てたデータファイルが自動で縮むわけではない。ファイルの空きをOSへ返す縮小は別操作であり、定期的な縮小は推奨されていない。[Microsoft公式資料](https://learn.microsoft.com/en-us/sql/relational-databases/databases/shrink-a-file?view=sql-server-ver16)

## 5. 現段階の結論

利用者の考え方で進める。対象外の過去研究の全再現・全データ整理は不要。結果を既存の小さな記録へまとめて保管し、二重にデータを増やさない。

SQL容量の削減は別の限定作業として行う。主な容量は優先研究でも使う可能性が高い共用データであるため、現在は削除候補の確定前。再計画P0の入力対応表と合わせて、不要な派生物・重複を狙って絞る。削除量や完了日を未確認の段階で断言しない。
