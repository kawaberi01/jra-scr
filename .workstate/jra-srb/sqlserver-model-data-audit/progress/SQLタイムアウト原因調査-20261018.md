# 共通履歴SQLタイムアウトの原因調査

作成日: 2026-10-18 JST。対象: progress041で停止した当日スカウトの履歴SELECT。原因確認のみ。

追記: 利用者の今回限りのsa許可による追加診断で、推定1行に対するNested Loopsと着順表の反復全走査を確認した。最新の原因・待機・計画証跡は[sa追加調査](SQLタイムアウトsa追加調査-20261018.md)を参照。以下は通常readerだけで行った初回診断の記録を保持する。

## 確認結果

接続は成功している。build_live_feature_recordsが発行する全過去履歴の4表結合が、設定された30秒のquery timeoutを超える。SqlServerConnection.executeは元の例外を汎用SqlServerStorageErrorへ置き換えるため、通常API応答だけではQuery timeout expiredが見えなかった。

同じreader・接続設定・対象日・取得列・条件・並び順を使い、SQL末尾へ診断限定のOPTION(HASH JOIN)だけを加えると9.075909秒で101,408行を取得した。通常計画選択を含む結合処理に強い性能依存があることを実測した。元計画のどの演算子・結合順序・推定件数が問題かは未確定。実行計画と待機状況を見ていないため、Nested Loopsの誤選択、特定索引の未使用、ロック競合、メモリ待ちなどの内訳を断定しない。

## 診断方法と実測

実コードからSELECTをASTで抽出し、既存compile_sqlでSQL Server版を生成した。既存readerを使い、DDL・業務更新・権限追加・timeout設定変更はしていない。SQLite接続・当日結果の読取・再学習・予想生成なし。

| 診断差分（各1回） | 結果 | 意味 |
|---|---|---|
| 元クエリ | 30.008296秒、OperationalError/query timeout | 単独実行でも再現 |
| ORDER BYのみ削除 | 取得が長時間継続し、診断の実プロセスを確認して停止 | 並び替えを外すだけでは取得完了しなかった。正確な完了時間は未測定 |
| re.rank IS NOT NULLのみ追加 | 30.037712秒、query timeout | filtered indexのNULL条件を満たすだけでは解消しない |
| OPTION(HASH JOIN)のみ追加 | 9.075909秒、101,408行取得成功 | 論理的な取得条件を維持した結合方式指定で完了 |
| OPTION(RECOMPILE)のみ追加 | 30.012428秒、query timeout | 古いキャッシュ計画を作り直すだけでは解消しない |

HASH JOIN版のNULL着順は842行。元コードは後段の_valid_rowで無効着順を除く。結果multiset SHA256はa01cec6fde06c1c8acbcf74d99793e74956d143e48f893d192bdb8fab2a297e2。元クエリは完了していないので、元出力との実取得全行一致検証を完了したとは扱わない。

ORDER BY削除版の長時間取得を受け、残る各測定には既存30秒のstatement timeoutに加え、専用診断プロセスの40秒wall limitを追加した。元クエリや同一差分の無根拠な反復は行っていない。

## 実DB・索引・権限

- 実DB: jra_unified、compatibility 160、auto create/update statisticsは有効。
- sys.partitions上の件数: races 8,025、runners 109,461、result_entries 102,692、payouts 88,680。今回のSELECT対象はapi_runtimeの運用4表。
- result_entriesの直接集計でも102,692行、NULL着順851行を確認。
- race_id/horse_no/race_date/sourceはnvarchar(max)。結合には元の文字列一致とpersisted binary(32) hashの一致条件が併用される。
- races: race_id hashのfiltered unique index、race_date/course hash索引。
- runners: race_id/horse_no hashのfiltered unique index。
- result_entries: race_id hash/rank/horse_no hashのfiltered unique index。rank IS NOT NULL等がfilter条件。
- payouts: race_id/bet_type hash索引。
- 無効化索引は確認されなかった。索引が存在することと、問題クエリで有効利用されることは別。
- 通常readerはSHOWPLAN=0、VIEW DATABASE STATE=0。推定計画採取は失敗。server stateのpermission結果はNULLで、待機情報は未採取。診断のための権限付与・管理loginへの切替はしていない。

## 全日処理を遅くする別要因

build_live_feature_recordsは1レースごとに同じ対象日前の全履歴をSELECTし、Python側で集計し直す。日付が同じなら共通化できるが、現行スカウトはレースごとに呼ぶ。SQL単体の問題が解消しても、今回の9秒を36回繰り返す方式では45秒の全日枠に収まらない。

APIスカウト内では同期の特徴量生成をasync関数から直接呼ぶ箇所もある。外側のasyncio timeoutだけでは、この同期SQL処理を即時中断できるとは限らない。全体45秒とSQL30秒は別の制限として扱う。

CatBoost・S06/S08の当日比較は同じbuilderに依存する。一方、R1専用CLIは年別rawのkeyset readerを使い、この結合クエリを通らないため、秋華賞の推論が成功したことと矛盾しない。

## 並行作業と未確認事項

記録時の006には、別作業のspec180研究run20261017T163427Z_79bd6188d33b46c19164600dd57840e8が実行中と追記されていた。共有006は上書きせず、この記録を独立保存した。今回、別プロセスの停止・変更はしていない。並行研究によるCPU/I/O/メモリ競合は測定していないため、実測値にはその影響が残り得る。ただし初回スカウトの失敗は01:27 JSTであり、01:34開始のこの研究だけが初回失敗の原因とは言えない。

その後manifestを確認し、同研究は01:34:27〜01:40:12 JST、status=completeと判明した。RECOMPILE版の測定は同研究の終了後でもタイムアウトしている。並行研究だけで現象全体を説明する根拠はない。

## 修正へ進む場合の方針（未実装）

1. 問題クエリを、既存のSQL分割読取・メモリ結合の実績がある部品と比較する。HASH JOIN指定は診断上の有力な手掛かりであり、全SQLへ一括適用しない。
2. 日付・入力版を固定して履歴を1回だけ読み、当日全レースへ共有する。取消等の当日カードは各レースの最新値を使う。
3. 正常取得したSQLの全行・順序と特徴量の同値性、当日結果の非参照、全36Rの実時間を確認する。タイムアウトの延長だけを解決としない。
4. 元計画の詳細分析にはSHOWPLAN/待機情報を読める診断経路が必要。今回はその権限・接続設定を変更していない。
