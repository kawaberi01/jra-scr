- `scripts/score_jra_j23_live.py`: `score`と`evaluate`を追加。HTTP取得・API起動・タスク登録はしない。取得済みのカード、単勝と馬連の`t_minus_30m` receiptが必要。
- `src/jra_srb/jra_research_j23_policy.py`: 既存の`band/estimate/policy_stake`を意味を変えず共通化し、連続する完全月だけから係数を作る`monthly_parameters`を追加。
- `scripts/analyze_j23_ten_aspects.py`: 上記3関数の定義を共通moduleからのimportへ変更。研究の計算式・購入条件・既存成果物を変更していない。過去監査のpolicy_source_sha256は当時のソースを指すため、過去監査JSONを書き換えていない。
- `tests/test_jra_research_j23_live.py`: 合成receipt/Store代替と実固定モデルで新入口を検証。

モデルは既存2026-09 J23の既知SHAだけをjoblibロードし、学習末尾2026-08-30を照合する。元30セルの内容SHA集合も固定して検査。R1入力をJ23として使わない。履歴は2003年から対象日前だけを日末更新し、公式カードの直近正常走より古い対象馬履歴を拒否する。長い履歴構築の後にSQL受領を再選択し、鮮度・T30締切・馬集合・負担重量等の不変を再検査する。

元ペアに対するJ23/Q03/Q06の式による候補賭金は`candidate_stake_yen`。現receiptでは公表時刻・同一T30 capture・統一ID対応・履歴公表時点を証明できないため、`runtime_validation_only`かつ`performance_eligible=false`、評価賭金`stake_yen=0`とする。条件不足を補完して購入成立にしない。

## 保存と事後比較

`score --save`は既存SqlServerAnalysisStoreを明示し、一意prediction_id、budget=0、実購入券空で参考予想を保存する。既存idempotency key/fingerprintと、予測と同一transactionで作られるwrite_receiptsを再利用。既存IDは保存前に拒否。予測・入力証跡・全馬連・モデル/係数SHAを読み戻し、commit後のSQLサーバ時刻もT30以前であることを確認する。created_atやcommit前受領時刻だけを保存完了証明にしない。

`evaluate`は元metrics SHAと、SQL保存した場合は受領本文SHA/受領時刻を再検証する。発走後の公式結果だけを読み、正常一意着順・同じ馬集合・明示馬連払戻を照合し、3政策の会計とJ23/M0のlogloss/Brierを別runに保存する。参考区分の評価賭金は0円のまま。元runと元予想を変更しない。締切価格は未取得で、払戻から逆算しない。

アプリケーションでID既存検査と受領照合をするが、既存upsert自体をDBの追記専用保証に変えたわけではない。

## 検証

最終実行:

```powershell
rtk uv run --frozen --extra ml pytest -q tests/test_jra_research_j23_live.py tests/test_j23_ten_aspects.py tests/test_jra_research_r1_live.py
```

**41 passed、4 warnings**。warningは既存joblibモデルのNumPy 2.5 shape復元に関するDeprecationWarning。学習・依存追加なし。

確認した主な契約:

- 非一様な合成特徴と実固定J23モデルで、研究matrixを使わない独立28列式/softmaxと確率一致。対象結果を注入しても推論不変。
- 市場明細の並び/ペア左右を変えても同じ馬番号と価格へ対応。Q03が見送っても別ペアへ再選択しない。
- 欠測月を飛ばさず、当月結果・不完全月を拒否。2026-10初期係数が既存値と一致。
- 重複/欠落/発売停止/取消未解決/T10代用/未来受領/鮮度超過/100nsの締切超過を拒否。
- SQL代替で既存ID拒否、実券空、payloadと受領本文SHA、commit後サーバ時刻、idempotency文脈復元を確認。
- カード属性変更時の停止、正常な入口から別評価runへの接続、元予測run全ファイルSHA不変、同着/不明精算の拒否、100円口数精算。
- `--help`と`score --help`の入口確認。Windowsでは`python -X utf8`を付ける。

実SQLの読取検証:

1. `20261023T014549Z_fe449bb6c3e04c9fa2877f2c070a0e49`: 固定34版/reader/receipt索引preflightは成功。指定した2026-10-18京都11Rの当該cutoff以前のreceiptは0行で、`j23_missing_official_receipt`として停止。履歴構築・推論・SQL保存へ進めていない。`input-diagnosis.json`へ0行の限定診断を保存。
2. 前回監査で保存確認済みの京都10Rを、別の「受領契約だけ」の読取検証として明示指定。`20261023T014846Z_c137a8c0224b417a86994855e4060faa`で14 receiptからカード/単勝/馬連3束の公式source・型・SHA・版を検査しpassed。T30以前の予測成立や性能測定として扱っていない。SQL更新0。

## 利用入口

対象日の発走30分前より前に、既存収集経路が公式カードと単勝/馬連を保存済みの場合:

```powershell
rtk uv run --frozen --extra ml python -X utf8 scripts/score_jra_j23_live.py score --date YYYY-MM-DD --course tokyo --race-no 11 --race-id API_ID --save
```

`YYYY-MM-DD`と`API_ID`は実際の対象へ置換する。`--save`を省略すると新規研究runだけを作る。結果保存後は:

```powershell
rtk uv run --frozen --extra ml python -X utf8 scripts/score_jra_j23_live.py evaluate --run-id FORECAST_RUN_ID
```
