# 共通履歴SQLのsa追加診断

作成日: 2026-10-18 JST。
前提: 利用者が今回の原因調査に限りsaによる接続を明示許可した。通常運用の接続方式は変更しない。

## 接続確認

- 既存のjra-van-data/infra/sqlserver2022-poc/README.mdとtools/sqlserver_unified_runtime.py、provision_sqlserver_migration_sample.pyを確認。
- Windows Process/User/MachineにSQL管理者用と識別できる環境変数は見つからなかった。既存helperが読むローカルinfra/sqlserver2022-poc/.envのMSSQL_SA_PASSWORDをメモリ上だけで取得した。
- 既存helperの固定先127.0.0.1,11446へ暗号化接続。DB=jra_unified、ORIGINAL_LOGIN=sa、sysadmin=1、major_version=16、SHOWPLAN=1を確認。
- 認証値・接続文字列・.env本文を出力や成果物へ記録しない。通常APIのruntime.env、reader/writer、DB権限を変更しない。

## 原因として確認できたこと

通常readerの元SELECTを1回だけ再実行し、saは対象reader sessionを観測するために使用した。01:51:53頃〜01:52:23頃JST、30.041856秒で同じquery timeoutを再現。

実行中計画にはNested Loopsとresult_entriesの反復したClustered Index Scanが含まれる。

| 箇所 | 計画の推定 | 約12秒時点の実績 |
|---|---:|---:|
| racesの対象条件Filter（Node12） | 1行 | 333行、まだ走査途中 |
| result_entries全走査（Node16） | 1回102,692行 | 333回実行、累計34,193,542行を出力 |
| 最終Sort（Node0） | 約1.00056行 | 上流取得中で出力0行 |

レース数を大幅に過小見積もりし、約10万行の着順表を繰り返し全走査する計画が、今回のSQL遅延の中心であると確認した。各レース側の行に対して反復走査する形になっており、30秒を超える。

取得できたFilter条件は、race_idの長さ、race_id内の場コードsubstring、sourceのprefix、race_dateの対象日前判定。同じ部分の型はnvarchar(max)を含む。どの述語・統計が推定1行を作る決定要因かは未分解。型変換に関するPlanAffectingConvert/Cardinality Estimate警告もあるが、その警告だけを唯一の原因とは断定しない。

result_entriesに既存のfiltered unique indexは存在するが、元計画は同表をClustered Index Scanで読む。rank IS NOT NULLを追加するだけでは前回30秒timeoutだったため、その条件だけの修正では足りない。

## 待機・負荷

4/8/12/16/20/24秒付近の6回、対象sessionのrequestとmemory grantを採取した。

- blocking_session_idは6回とも0。観測時点で他sessionのロック待ちは確認されなかった。
- 約12秒でCPU 11,528ms、経過12,041ms、logical_reads 968,383。
- 約24秒でCPU 18,980ms、経過24,109ms、logical_reads 1,549,569、reads 2,161。
- 主なlast_wait_typeはSOS_SCHEDULER_YIELD。20秒付近にはPAGEIOLATCH_SHを観測し、物理読取も発生。
- 要求メモリ1,024KB、割当1,024KB、GrantWaitTime=0。メモリ割当待ちは確認されなかった。Sortの推定件数も過小だが、完走していないため最終的なspillの有無は未確認。

少なくともこの再現では、接続失敗やロック待ちを中心とする説明ではなく、反復走査のCPU・論理読取・一部I/Oが証跡に一致する。

## HASH JOIN版との比較

saで対象SELECTだけのキャッシュ計画も採取した。完走済みのHASH JOIN版は、3つのHash Matchと各表の走査を組み合わせる。SQL Server内のlast_elapsed_timeは7,707.23ms、last_logical_readsは23,111。前回のアプリ側全取得実測は9.075909秒、101,408行。

通常版の約24秒途中で1,549,569 logical readsに対し、HASH JOIN版は完走で23,111。通常版の過小見積もりに由来する反復走査と対照的で、前回の「結合方式が有力原因」という推定を実行中計画で裏付けた。取得条件を緩めたり当日結果を足したりしたものではない。

HASH JOIN版でも最終推定件数は約1行のままで、推定件数自体の問題を直したことにはならない。本番に恒久適用したわけではない。元版は未完走なので、全行出力の実測同値比較も未完のまま。

## 実施範囲と次の方針

- 実施: 既存sa接続でのidentity、限定したcache plan、索引filter定義、統計情報、通常readerの実行中計画と対象session DMVのSELECT。
- 変更なし: DBデータ、schema/index、統計更新、権限、trace flag、Query Store、API設定、モデル、既定スキル。KILL・再起動・他プロセス停止なし。
- 全日スカウトは再実行していない。購入候補や予想値も生成していない。
- 修正へ進む場合は、問題クエリに限った取得方式の改善と、同一日付の履歴を1回だけ読んで全レースへ共有する処理を分けて扱う。既存のkeyset読取・メモリ結合の経路を優先して比較する。
- 単純なtimeout延長やsaへの通常運用切替は解決策として採用していない。今回のsa接続は診断終了時に閉じた。
